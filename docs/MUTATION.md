# Layout-mutation campaign (docs/spec/VERIFICATION.md section 2, "the TEMPO move")

Generated by `test/mutation/campaign.py` (seed `20260918`) on 2026-09-18. 130 mutants,
10 operators x 2 designs (warm-up `upstream/warmup/04_final.gds`, puzzle
`upstream/puzzle.gds`), full run with `--verilator-every 1` (every applicable V6 check
run, not just a sample): **119.2 s** wall clock with 18 worker processes on an 18-core
box, well inside the ~40-minute budget. `out/mut/results.json` is the raw data this
report is generated from; `out/mut/<id>/` holds each mutant's GDS, emitted netlists, and
(for the warm-up) its own copy of the SBY formal run.

The question this campaign answers: **if the extraction were wrong in a particular way,
would at least one of our check layers notice?** Each mutant plants one deterministic
fault in a *copy* of a real design GDS (never the shared `upstream/` files) and every
applicable check layer from `docs/spec/VERIFICATION.md` §1 is run against that mutant,
independently, from scratch. This never calls the `functools.cache`-wrapped fixtures in
`test/test_*.py` (those are pinned to the two real designs); it calls the same underlying
library functions (`Extraction`, `read_def`, `tools.l2n.compare`, `tools.retrace.netgraph`,
`iverilog`/`vvp`, `verilator`, `sby`) directly against each mutant's own path, and every
mutant is asserted byte-different from the original before it is scored.

## Method

**Site selection.** `tools/retrace/mutate.py` enumerates every geometrically valid site
for an operator from a real `Extraction` of the base design (real signal nets, real
paths, real via instances -- never random coordinates), sorts them deterministically,
and `test/mutation/campaign.py` samples `min(6, len(pool))` (warm-up) or `min(7,
len(pool))` (puzzle) of them with `random.Random(f"{seed}:{design}")`. Every operator on
every design had far more candidates than the target (see the candidate-pool table
below), so all 20 (operator, design) combinations got the full 6 or 7 sites -- the "fewer
only if the design has fewer valid sites" fallback in the brief was never needed.

**Classification.**
- **killed**: at least one check layer failed on the mutant.
- **equivalent**: no layer failed, *and* the mutant's extracted net partition and its
  (master, x, y, orientation) instance multiset are byte-for-byte identical to the
  original's -- i.e. the mutation had no electrical effect at all (a redundant via, a
  deleted pixel-art square).
- **survived**: no layer failed, but the partition or instances *do* differ -- a real,
  unproven gap.

**Check layers run per mutant**, all from the real library code (never re-implemented):
diagnostics (`Extraction.diag`), `cellcheck` (masters vs `pdk/.../sky130_fd_sc_hd.gds`),
`V2_pins` (LEF pin-name set *and* per-rectangle owner, i.e. `test_pins.py`'s two checks
combined), `V4_extractors_agree` (gdstk vs KLayout L2N). Warm-up only: `V1_placements`
(vs the golden DEF), `V3a_partition` (net partition vs DEF), `V3b_isomorphism` (labelled
graph vs `01_netlist.v`), `V3c_formal` (SymbiYosys `abc pdr`, run in the mutant's own
`out/mut/<id>/warmup_equiv/` so it never touches the shared `formal/warmup_equiv/`).
Puzzle only: `V5_sanity` (driver/floating-input/supply checks), `V6_icarus` (VCD replay),
`V6_verilator` (second simulator, Liberty-derived logic).

## Per-layer kill contribution

Counted over the 91 mutants that were *not* classified equivalent (an equivalent mutant
has nothing for any layer to catch, so it is excluded the same way TEMPO's report
excludes suites a module doesn't apply to). This is the "unit tests alone 93%"-style
breakdown:

| layer | applicable (non-equivalent, non-error mutants) | killed | rate |
|---|---|---|---|
| `diagnostics` | 91 | 0 | 0% |
| `cellcheck` | 91 | 26 | 29% |
| `V1_placements` | 42 | 24 | 57% |
| `V2_pins` | 91 | 13 | 14% |
| `V3a_partition` | 42 | 42 | 100% |
| `V3b_isomorphism` | 42 | 42 | 100% |
| `V3c_formal` | 42 | 39 | 93% |
| `V4_extractors_agree` | 91 | 19 | 21% |
| `V5_sanity` | 49 | 33 | 67% |
| `V6_icarus` | 49 | 29 | 59% |
| `V6_verilator` | 49 | 28 | 57% |
| **any layer** | 91 | 90 | 99% |

Read by design: on the **warm-up**, which has ground truth, `V3a_partition` and
`V3b_isomorphism` alone catch 100% (42/42) of the non-equivalent mutants, and `V3c_formal`
(the one check with no name map at all) catches 93% (39/42) -- consistent with the
existing pytest suite, where a planted mux2 input swap is the one documented case V3c
must be able to see (`docs/STATUS.md`). On the **puzzle**, which has no golden netlist,
`V5_sanity` (67%) and the two independent VCD-replay simulators (`V6_icarus` 59%,
`V6_verilator` 57%, largely the *same* mutants -- see "Conclusions") carry the weight that
V1/V3 carry for the warm-up.

`diagnostics` killed 0/91: none of the ten operators happens to produce the specific
malformed shapes (`pin_label_without_polygon`, `label_unbound`, `cut_open_*`,
`port_label_conflict`) that trip the extractor's own internal counters -- those need an
operator that removes or displaces a *label*, which none of the ten does (the closest,
`pin_label_swap`, relocates a label's *text*, not its geometry, so the label still sits on
a polygon). This is a real coverage note for a future operator, not a failure of this
campaign.

## Survivors

- `puzzle_master_swap_00` (puzzle/master_swap): swapped master nor2_2 -> nand2_2 at DEF (185.380,19.040) S -- same footprint width/height, behavioural change, identical connectivity
    - diagnostics: PASS 
    - cellcheck: PASS 
    - V2_pins: PASS 
    - V4_extractors_agree: PASS 
    - V5_sanity: PASS 
    - V6_icarus: PASS 
    - V6_verilator: PASS

**Analysis.** `master_swap` replaces one instance's master with a different master of
identical footprint width/height and (for this campaign's 4 validated pairs) identical or
positionally-equivalent pins -- same physical placement, same physical connections, only
the truth table changes (nand2_2<->nor2_2, xor2_2<->xnor2_2, and3_2<->or3_2,
nand3_2<->nor3_2). This is, by construction, **invisible to every structural or electrical
check**: `cellcheck` compares named masters (both `sky130_fd_sc_hd__nand2_2` and
`sky130_fd_sc_hd__nor2_2` are real, valid PDK masters, so no per-master geometry check
fires), `V2_pins` and `V4_extractors_agree` only see conductor geometry, which is
identical, and `V5_sanity` only checks driver/floating-pin structure, which is also
identical. Only a *functional* check can tell nand from nor.

On the **warm-up**, 6/6 `master_swap` mutants were killed anyway, because there a
functional check comes for free at zero marginal cost: `V1_placements` and
`V3a_partition` compare the *instance name itself* (a swapped master is a different
string in the (master, x, y, orient) tuple), and `V3b_isomorphism`'s node label is the
cell type, so a swap is instant non-isomorphism. `V3c_formal` (the one *purely
behavioural* proof, with no name map) independently also caught 5/6.

On the **puzzle**, none of that exists -- there is no golden DEF, no golden netlist, so
V1/V3a/V3b/V3c have no puzzle equivalent (`docs/spec/VERIFICATION.md` V1-V3 are explicitly
warm-up-only; the puzzle relies on V4/V5/V6). `master_swap` there depends entirely on
`V6_icarus`/`V6_verilator` noticing that the swapped gate's output actually flips one of
`O[7:0]`/`success` differently, for the *one* recorded stimulus
(`upstream/example_inputs.vcd`). 6/7 puzzle `master_swap` mutants were still caught this
way -- but `puzzle_master_swap_00` (nor2_2 -> nand2_2 at DEF (185.380, 19.040), orientation
S) was not: both simulators, run independently (Icarus against the PDK Verilog models,
Verilator against Liberty-derived logic, confirmed with a dedicated re-run, not just the
sampled pass), replay all 1248 checkpoints of the VCD with 0 mismatches, identically to
the un-mutated netlist.

This is a real, documented gap, and it is exactly the gap `docs/STATUS.md` already flags
under finding 6: **`success` never rises in `example_inputs.vcd`**, and the trace only
exercises two 121-cycle "TRY AGAIN" runs -- it is nowhere close to exhaustive over the
puzzle's 728 logic cells. A `master_swap` on a gate whose output only affects a bit
pattern this one trace never produces (or produces identically under both truth tables
for the input combinations actually seen) is undetectable by any check this project
currently has for the puzzle. This is the reason V4 (two independent extractors) is load-
bearing evidence for *connectivity* correctness (STATUS.md already frames it this way),
but it was never meant to, and does not, stand in for functional coverage -- closing this
gap needs either more/better stimulus (S4's synthetic OpenLane designs, mentioned in
`docs/spec/VERIFICATION.md` §3) or the Sprint 3/4 RTL-recovery work (V7/V8), which will
give the puzzle a from-source golden model to formally equivalence-check against, the way
the warm-up already has one.

## Equivalent mutants

39/130 (30%) had zero electrical effect. By operator, this was not spread evenly -- three
of the ten operators were equivalent at **every** site tested, both designs, 14/14 each:

- **`art_delete`** (14/14): exactly as expected going in -- the 1366 met2 squares are
  floating pixel art that touches no signal net in either design (`docs/STATUS.md` finding
  5), so deleting one changes nothing any check layer looks at.
- **`path_endtype`** (14/14): flipping a path's end type between `extended` and `flush`
  changes the cap by about half the path's width at each end. In every one of the 14 real
  sites tested (chosen only by "lands on a signal net", not by proximity to a via/pin),
  that was inside the routing's existing clearance -- it neither opened a connection nor
  created a new touch. This says more about *this operator's site selection* than about
  the check layers: a version that specifically targets a path end sitting flush against a
  via/pin boundary (rather than mid-route) would be a sharper test of V3a/V3c/V6's
  sensitivity to end-type changes, and is a natural follow-up.
- **`path_shift_nearmiss`** (14/14): a 5-20 nm perpendicular shift of one path endpoint,
  at all 14 real sites tried, never separated a real touch. This is a genuinely
  informative negative result, not a weak operator: OpenROAD's routing (used to build both
  the warm-up and the puzzle) keeps enclosure/overlap margins at contacts and vias well
  above the single-digit-to-20 nm scale this operator perturbs at, precisely so that
  sub-DRC-rule manufacturing variation of this size can never open a connection. The
  operator would need to move by tens to hundreds of nm (past that margin) to have a
  chance of opening something -- which `via_delete` and `path_widen_short` already test
  more directly, and did: every `via_delete` and `path_widen_short` mutant (26/26 total)
  was killed.

The other seven operators produced a mix of killed/(1 survived) mutants, as in the
operator table above -- none of them was ever classified equivalent.

## Deviations from the brief

- **`and2_2`<->`or2_2` is not a valid `master_swap` pair in this PDK revision.** The brief
  gives it as an example, but in the pinned PDK (open_pdks `8afc8346`, see
  `docs/STATUS.md`), `sky130_fd_sc_hd__and2_2` is 2.760 um wide and `sky130_fd_sc_hd__or2_2`
  is 2.300 um wide -- different footprints, not a same-footprint drop-in swap. Verified
  directly against `pdk/sky130_fd_sc_hd/lef/sky130_fd_sc_hd.lef`. `master_swap` instead
  uses four pairs actually verified same-width/same-height and same (or positionally
  equivalent) pins in this PDK: `nand2_2`<->`nor2_2`, `xor2_2`<->`xnor2_2` (both from the
  brief), plus `and3_2`<->`or3_2` and `nand3_2`<->`nor3_2` (both 2.76 um resp. 3.68 um in
  both cells, checked the same way) to make up for the dropped pair.
- **`nand2b_2`<->`nor2b_2`** (also plausible from the brief's "e.g.") was checked and
  *not* used: same footprint width (3.22 um) but different pin roles (`A_N`/`B` vs.
  `A`/`B_N`), so it is not a physically-equivalent drop-in the way the four pairs above
  are.

## Methodological caveats (read before trusting a "killed by cellcheck/V6" line at face value)

- **`pin_label_swap` and `cell_internal_tamper` require a private copy of the master
  ("new cell name, one instance re-pointed at it" per the brief), and that new name is
  never a real PDK master.** `cellcheck` and Icarus/Yosys ("Unknown module type") both
  correctly flag every one of the 26 mutants from these two operators, and it is fair to
  read that as "the naming convention alone would already catch this," not proof that an
  in-place edit under the *original* cell name would also be caught. It would be, though,
  independently: `V2_pins`'s per-rectangle-owner check (the extended, exact version --
  `check_v2_pins` in `test/mutation/campaign.py`, matching `test_pins.py`'s
  `test_v2_lef_rects_on_extracted_pin`) catches every `pin_label_swap` mutant on its
  geometric content alone (e.g. `sky130_fd_sc_hd__a31o_2__PINSWAP_0.A1 (li1): expected
  owner 'A1', got ['A2']`), independent of the renamed cell -- this is checked by
  extending the LEF lookup (`mutate.lef_for_mutant`) with a synthetic entry that reuses
  the *original* master's footprint for the private copy, so V2 compares the tampered
  geometry against the unmodified expectation. `cell_internal_tamper` (deleting one poly
  or licon shape) is caught by `cellcheck`/naming in every case tested here, but was not
  independently confirmed on geometric grounds alone the way the pin swap was -- a real
  gap in this campaign's rigor for that one operator, noted rather than glossed over.
- **`via_insert_short` can hang a zero-delay simulator.** One puzzle mutant
  (`via_insert_short`, `VIA_M1M2_PR` shorting two actively-driven nets) made `vvp -n`
  spin on delta-cycle contention instead of erroring, observed at ~70 s before the
  timeout was tightened; `check_v6_icarus`/`check_v6_verilator` now cap the simulation
  run itself at 25 s and count a timeout as a kill (a real, honest one -- the short *is*
  a fault, and hanging a zero-delay simulator is a legitimate way for a check to notice
  it). All `via_insert_short` mutants were independently also killed by `V5_sanity` well
  before this became a bottleneck.
- **A real bug this campaign found in itself.** Two warm-up mutants
  (`warmup_master_swap_03`, `warmup_pin_label_swap_02`) both happen to move the design's
  *only* instance of `sky130_fd_sc_hd__and3_2` away to a different/private master,
  orphaning `and3_2` in the mutant library. `gdstk.Library.top_level()` (and KLayout's
  `Layout.top_cell()`) then report **two** top-level cells, and `Extraction(gds, lef)`'s
  default (`top=None` -> the first one) sometimes picked `sky130_fd_sc_hd__and3_2` itself
  instead of `adder_demo` -- silently extracting a 4-pin combinational cell instead of the
  real design. It surfaced first as a reproducible (not flaky -- identical on two
  independent full runs) `ERROR: Module 'adder_demo' not found!` from Yosys during
  `V3b_isomorphism`, and on investigation `V4_extractors_agree` for the same two mutants
  was also silently wrong (a `RuntimeError` from KLayout once explicit `top=` was added
  and it could no longer guess). Fixed by always passing `top=TOP_NAME[design]` explicitly
  to every `Extraction(...)` call in `test/mutation/campaign.py`; both mutants were
  re-run and their entries in `out/mut/results.json` are from the corrected run (both were
  already correctly classified `killed` before and after -- only the per-layer attribution
  was wrong). This is exactly the kind of thing a mutation campaign is supposed to shake
  loose, including in its own harness.

## Reproducing

```
export PATH=~/ttsetup/oss-cad-suite/bin:$PATH
.venv/bin/python test/mutation/campaign.py --list          # candidate/selected counts only
.venv/bin/python test/mutation/campaign.py                 # full run -> out/mut/results.json
.venv/bin/python test/mutation/campaign.py --quick 6        # first 6 mutants, for debugging
.venv/bin/python -m pytest -q test/test_mutation_smoke.py   # 3-mutant regression net, <30 s
```

Run as a plain script, not `-m test.mutation.campaign` -- the Python stdlib also ships a
`test` package and this project's `test/` has no top-level `__init__.py`, so `-m
test...` can resolve to the wrong `test` package first (see the module docstring in
`test/mutation/campaign.py`).

## Conclusions

- **For the warm-up, structural checks against ground truth (V1/V3a/V3b) and the one
  purely behavioural proof with no name map (V3c) together are effectively total**: 100%
  (V3a, V3b) and 93% (V3c) of the 42 non-equivalent warm-up mutants, any-layer 100%
  (42/42). This matches, and stress-tests, the "PASS becomes FAIL" claim already made
  informally in `docs/STATUS.md`/`test_warmup.py` (a planted mux2 input swap fails V3c) --
  here it holds over 42 independently planted faults across all ten operator classes, not
  one hand-picked example.
- **For the puzzle, V5 (electrical sanity) and two independently-implemented VCD-replay
  simulators (V6) carry the weight** that ground-truth checks carry for the warm-up (67%,
  59%, 57% respectively of 49 non-equivalent puzzle mutants; any-layer 98%, 48/49). `V4`
  (cross-extractor agreement) is real, complementary evidence specifically for
  *connectivity* faults (opens, shorts, orientation) -- it caught every `cell_flip` and
  contributed to several `master_swap`/`via_delete` kills -- but, correctly, contributes
  nothing to catching a same-connectivity behavioural change; that is V6's job alone.
- **The one confirmed, unfixed gap**: a same-footprint, same-connectivity logic swap
  (nand<->nor family) on the puzzle is invisible to every check layer this project has
  *unless* the one recorded stimulus happens to exercise the swapped gate's output
  differently, and for one of the seven sites tested, it does not. This is not a flaw in
  the checks so much as a direct, expected consequence of the puzzle having no golden
  netlist and only one (non-exhaustive, `success`-never-observed) input trace --
  See the lead-review addendum below for what does and does not close it.
- **Two negative results are themselves informative, not weak spots**: `path_endtype` and
  `path_shift_nearmiss` (28 mutants combined) never produced a real electrical difference
  in this design, at the scale/site-selection this campaign used. For `path_shift_nearmiss`
  this is evidence the PnR flow's enclosure margins comfortably exceed the 5-20 nm scale
  tested (a good sign about the routing, not a gap in the checks -- `via_delete` and
  `path_widen_short`, which test opens/shorts more directly, killed 26/26). For
  `path_endtype` it is more a note about site selection (mid-route vs. at a via/pin
  boundary) than about routing margin, and is the clearest concrete follow-up this
  campaign surfaces.
- **`diagnostics` (the extractor's own internal sanity counters) never fired** across all
  91 non-equivalent mutants -- none of the ten operators happens to produce the specific
  malformed-label shapes those counters watch for. Not a failure, just uncovered by this
  operator set; noted for anyone adding an eleventh operator.

## Lead-review addendum (2026-09-18)

An independent review agent re-ran 8 mutants by hand, the smoke test and the full
suite, and found the numbers trustworthy. Its one note: gdstk may write a rewritten
straight path back as a boundary (polygon) rather than a PATH element, so a geometry
audit of `path_widen_short`/`path_endtype` mutants has to compare conductor shapes, not
element types. The lead review adds:

* **The survivor is not an extraction failure mode.** `master_swap` models a
  *different chip*: masters are read by name from the GDS references, and `cellcheck`
  confirms their geometry matches the PDK. Every extraction-level check (V1-V5, and V7,
  which proves the recovered RTL equal to whatever netlist was extracted) is correctly
  blind to it, so an earlier draft's claim that V7 would close this gap was wrong. Only a
  behavioural oracle can see it, and the sample VCD does not exercise that gate.
* **The recovered design now serves as that oracle for regressions.** With
  `rtl_recovered/` proven equal to the original extraction,
  `python -m tools.analysis.e2e --gds out/mut/puzzle_master_swap_00/puzzle.gds` asks "is
  this layout still the design we recovered?" and **fails** (flop assertions at
  `recovered_miter.sv` lines 385 and 388), while the real puzzle passes. For future
  changes to the extractor or the GDS, the end-to-end proof kills this mutant class.
